- Use `uv` for managing Python dependencies. I've previously worked with `pip` + `pip-tools` and while it certainly worked, updating dependencies usually took a couple minutes each time as `pip-compile` performed its work to find matching dependencies. As this is a greenfield project, I've decided to use the more modern and hopefully quicker `uv`.
- Use Django REST Framework (DRF) along with Django. The choice was between Django alone, DRF + Django, or Django + Django Ninja. As I would like to separate the frontend from the backend, using raw Django was decided against because I would likely have to duplicate functionality already provided by DRF or Django Ninja anyway. In choosing between DRF and Django Ninja, I ultimately chose DRF as it is more mature and production-tested compared to Django Ninja, and this application doesn't require the features that Django Ninja provides.
- Use Docker Compose for deploying the Django app along with a PostgreSQL DB. While in a production environment it would be appropriate to use Kubernetes for deploying and managing the application, Docker Compose is simpler to setup for local development.
- Keep secrets in a gitignored .env file. Other approaches such as a cloud-agnostic approach using Hashicorp Vault or a cloud-provided solution such as Azure Key Vault or AWS Secrets Manager may make sense for production but add complexity that is not required for this project.
- Use the `postgres:18.6-alpine` image from Docker Hub. I'm not extending the image so I don't have to worry about musl libc compatibility and the smaller image size is a nice bonus. I've chosen to be explicit about the PostgreSQL version but not the Alpine version as it doesn't really matter which distro backs the image but it does matter which version of PostgreSQL I have access to.
- Set `shm_size` to 256MB for the PostgreSQL container. `/dev/shm` is used particularly for parallel queries and the example `compose.yaml` file in the image's docs uses 128MB while explicitly pointing out the possibility of exhausting shared memory with the default size of 64MB. 256MB is chosen to provide a little extra room to grow; this value may need to be changed depending on actual queries ran in production.
- Use Django's built-in web server. This is good for development, and I don't plan on running this application in production (although other than the web server it should theoretically be production-ready). Django explicitly recommends Apache, while also giving lots of other examples of possible deployment options.
